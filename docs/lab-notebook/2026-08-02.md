## E011 invalidated the safe-count assumption

E010 recovered the tested zero-payload workloads with
`maxExportBatchSize=100`, but that value was only a count proxy for a byte
limit. E011 registered a new payload dimension before execution to ask whether
the same 100-span chunk remains durable as one string attribute grows.

`RunDescriptor` gained `payloadAttributeBytes`, with zero as the legacy decode
default. The app validates 0...65,536, generates an ASCII `lab.payload` value of
that exact length on every span, records the value in the UI and immutable run
metadata, and exposes it through the background-transition runner. Reliability
Core tests and the regenerated Simulator build passed before evidence capture.

The accepted matrix held total spans and batch count at 100:

| Persistence | Payload / span | Flush | File | Received |
|---|---:|---:|---:|---:|
| Instant | 0 | 55.78 ms | 107,789 bytes | 100/100 |
| Instant | 1,024 | 48.17 ms | 213,715 bytes | 100/100 |
| Instant | 1,536 | 48.88 ms | 0 | 0/100 |
| Instant | 2,048 | 49.36 ms | 0 | 0/100 |
| Default | 1,024 | 51.93 ms | 213,688 bytes | 100/100 |
| Default | 1,536 | 49.04 ms | 0 | 0/100 |

Every background event preceded the 15-second schedule. Loss conditions made
no HTTP attempt before or after relaunch and left no persistence file. Flush
still completed, with durations overlapping successful conditions.

Adding 1,024 bytes to each of 100 spans increased the instant file by 105,926
bytes. Extending the observed shape by another 512 bytes per span projects an
object near 264,915 bytes, just above the 262,144-byte ceiling. The actual
1,536-byte runs then supplied the stronger observation: zero durable bytes and
zero receipts for both presets.

The conclusion is deliberately narrower than “large attributes are bad.” At a
fixed count of 100, one plausible schema change moved durability from complete
to absent without changing the apparent flush result. Count configuration alone
cannot enforce a byte contract.

## E012 recovered the same payload by changing object partitioning

E012 preregistered a matched intervention before execution. It kept total spans,
payload, preset, real background callback, unavailable collector, direct
`SIGKILL`, and relaunch procedure fixed, and changed only
`maxExportBatchSize` from 100 to 50.

All four registered conditions recovered exactly:

| Persistence | Payload / span | Flush | File | Request | Received |
|---|---:|---:|---:|---:|---:|
| Default | 1,536 | 119.46 ms | 264,897 bytes | 183,618 bytes | 100/100 |
| Default | 2,048 | 123.86 ms | 316,057 bytes | 234,818 bytes | 100/100 |
| Instant | 1,536 | 82.22 ms | 264,891 bytes | 183,618 bytes | 100/100 |
| Instant | 2,048 | 215.90 ms | 316,107 bytes | 234,818 bytes | 100/100 |

No first process made an HTTP request. Each relaunch made one successful request
and produced no missing, duplicate, unexpected, or generation-gap sequence.

One initially surprising observation strengthened the source interpretation:
the persistence files were roughly 265 or 316 KB, larger than the 256-KiB
object ceiling. That is expected because two individually valid 50-span objects
were appended to one file. The separate file limit is 4 MiB. On resume, the two
objects were flattened into one OTLP body, so partitioning storage did not add a
second observed transport request.

This E011/E012 pair is the cleanest intervention so far: the same logical data
moved 100/100 → 0/100 when encoded bytes crossed a hidden boundary, then 0/100
→ 100/100 when only the persistence-object partition changed. It also shows why
batch 50 is not a final answer. A single span may be oversized even at batch 1,
and future attribute changes can invalidate another fixed count.

## E013 found the count-tuning limit at one span

E013 extended only the automation input guard, from 65,536 to 524,288 payload
bytes, then ran exactly one span with `maxExportBatchSize=1`. The registered
240-KiB boundary-inside controls recovered 1/1 for both presets. Their
persistence objects were 246,874 and 246,876 bytes.

At a 256-KiB attribute, both presets completed provider flush but produced no
file, no HTTP attempt, and 0/1 recovery. The instant 300-KiB replication did the
same. The successful and failed default conditions took 113.02 and 112.08 ms,
so latency again concealed the boundary.

This closes the fixed-count escape hatch. A processor cannot split one
`SpanData`; every count limit including one admits a payload that exceeds the
writer's byte contract.

## E014 introduced an explicit byte contract outside the SDK

E014 preregistered a wrapper above the unmodified official Persistence
Exporter. ReliabilityCore gained a generic byte-budget partitioner, immutable
policy metadata, automation parsing, and a JSONL policy-event model. The first
implementation linearly encoded every candidate prefix using the same
`JSONEncoder([SpanData]) + comma` representation as persistence 2.5.0.

Accepted decisions are written and synchronized before forwarding a chunk.
Single oversize decisions record call/decision ordinal, encoded bytes, budget,
sequence, and span ID, then return exporter failure without invoking the writer.
The runner verifies that accepted bytes are at or below budget, rejected bytes
are above it, and accepted plus rejected sequences cover the generated ledger
exactly once. Policy evidence must remain byte-identical across relaunch.

There were two implementation mistakes worth preserving:

1. The first app build defined async protocol methods that called same-named
   synchronous methods. Swift 6 resolved the calls as async recursion and
   required `await`. The pinned Persistence exporter itself implements the
   synchronous surface only, so the unnecessary overrides were removed.
2. Extending the runner to a twelfth argument initially left a closed `if`
   condition before the new clause. `bash -n` caught the stray `&&` before any
   experiment ran.

All E014 runtime hypotheses then held. The payload-heavy E011 comparator was
split 98 + 2 and recovered 100/100 for both presets without lowering the
processor's batch 100. The E009 500-span comparator kept processor batch 256;
its two calls became 243 + 13 and 242 + 2, recovering 500/500 for both presets.
Every accepted object was no larger than 262,144 bytes.

The single 256-KiB span remained undeliverable, but was no longer silent. The
default policy measured 263,257 bytes and Instant 263,259, then recorded one
`rejectedOversize` identity each. Both stayed 0/1 with no persistence or HTTP
file. This is observability recovery rather than delivery recovery.

The linear algorithm exposed a serious cost: 0.91–2.07 seconds at 100
payload-heavy spans and 4.50–7.04 seconds at 500 ordinary spans. Exactness alone
was therefore insufficient for a mobile background intervention.

## E015 retained exactness and removed most search cost

## E016 measured queued main-thread work instead of inferring it

E016 added a backward-compatible `mainQueueProbeEnabled` run dimension. The
controller records one scheduled lifecycle event immediately before provider
flush, enqueues a closure on `DispatchQueue.main`, then performs the existing
synchronous call. The closure records its monotonic delay when the main queue
can execute it. The runner waits for and validates exactly one ordered pair
before sending `SIGKILL`; the pair must remain byte-identical after relaunch.

ReliabilityCore grew from 27 to 29 tests. The first Simulator build attempt
failed before compilation because the sandbox could not access CoreSimulator
and SwiftPM diagnostic caches. Repeating the same build with the required Xcode
permissions succeeded, so this was recorded as an environment failure rather
than an implementation failure.

All four registered conditions recovered exactly:

| Persistence | Policy / batch | Flush | Main-queue delay | Beyond flush | Received |
|---|---|---:|---:|---:|---:|
| Default | SDK native / 100 | 72.964 ms | 297.104 ms | 224.139 ms | 500/500 |
| Instant | SDK native / 100 | 129.497 ms | 374.177 ms | 244.680 ms | 500/500 |
| Default | Binary byte budget / 256 | 476.153 ms | 702.835 ms | 226.683 ms | 500/500 |
| Instant | Binary byte budget / 256 | 968.004 ms | 1,271.137 ms | 303.134 ms | 500/500 |

Every run made zero first-process HTTP attempts, had one file before direct
`SIGKILL`, resumed with one 138,591-byte request, and reconciled without loss,
duplicates, or unexpected identities. The binary conditions retained the
243 + 13 + 242 + 2 partition.

Two preregistered responsiveness claims failed and remain accepted evidence.
The delay beyond `forceFlush` was not below 100 ms in any condition. More
importantly, Instant binary completed the provider call just under one second
but did not execute the already-enqueued closure until 1.271 seconds. Provider
duration alone therefore understated the measured main-queue delay.

This does not prove visible frame or touch latency because the app was entering
background. The residual 224–303 ms can include the completion evidence write,
the rest of the lifecycle callback, and Simulator/OS scheduling. The next
intervention should move expensive work away from the main actor and preserve a
separate durability-completion signal rather than blocking the callback.

## E018 found order-dependent fragmentation before runtime

E018 added constant, alternating, primary-first, and secondary-first payload
patterns. Run metadata now stores the pattern and secondary byte count with
legacy defaults; launch parsing, the controller, UI, telemetry generation, and
the background runner carry them. Payload length is a deterministic function of
run ID metadata and sequence.

The first model compile failed because the pattern switch followed precondition

Renaming them made all 39 tests in 11 suites pass before the cost probe ran.

The registered mixed model used ten 143,360-byte payloads and ten 102,400-byte

| Order | Objects | Encoded bytes across objects |
|---|---:|---:|
| Alternating | 10 | 2,458,191 |
| Primary first | 15 | 2,458,201 |
| Secondary first | 15 | 2,458,201 |

## E019 isolated the upstream export-call boundary

E019 kept 500 synthetic 1,024-byte payloads and the 262,144-byte budget fixed,
then delivered them to the same additive policy through processor-sized calls:

| Processor batch | Export calls | Objects | Chunk counts |
|---:|---:|---:|---|
| 500 | 1 | 3 | 248 + 248 + 4 |
| 256 | 2 | 3 | 248 + 8 / 244 |
| 100 | 5 | 5 | 100 × 5 |
| 50 | 10 | 10 | 50 × 10 |

The wrapper never joined elements across the slash because they arrived in
different export calls. Five and ten small upstream batches therefore forced
five and ten underfilled persistence objects. This is a separate constraint
from the encoded-byte ceiling.

The preregistered batch-256 prediction expected four objects based on E015's
actual `SpanData` shape. It failed: the synthetic second call's 244 elements
were 257,178 bytes and fit in one object. The model still proves the call
boundary, while the mismatch warns against using a synthetic element to choose
a near-limit production threshold.

All four conditions covered 1...500 exactly once, binary and additive decisions
matched per call, and no object exceeded budget. Object count is not file or
request count; prior E010 evidence already showed many storage objects can be
appended and flattened later.

## E020 tested whether the evidence itself notices damage

E020 added a read-only manifest verifier and a mutation harness that copies the
accepted E016 Default/native run into fresh temporary directories. The control
verified 20 files. Removing the last lifecycle line caused a SHA mismatch,
adding an unlisted file caused an inventory mismatch, and deleting a listed
HTTP evidence file caused a missing-file failure.

The intentionally stronger mutation changed `collector.log` and replaced its
expected manifest digest. It passed, as preregistered. A local hash beside local
data detects one-sided or accidental changes, not a coordinated rewrite by
someone who controls both.

The harness rehashed the committed E016 source before and after all cases and
confirmed it was unchanged. A repository-wide audit then exposed one historical
format gap: E000 recorded its Collector hash in prose before SHA tables were
standard. The raw log still matched. Adding that same digest as a table row
brought the whole inventory under one verifier:

```text
verified_runs=75
verified_files=1142
```

This makes the missing GitHub push more than a publishing inconvenience. The
manifest checks raw files, a Git commit anchors the manifest, and an external
remote or observer anchors that commit history. Coordinated local rewrite
remains indistinguishable until the latter exists; signed and independently
retained history would be stronger still.
