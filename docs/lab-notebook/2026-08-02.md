# Lab notebook — 2026-08-02

## E011 invalidated the safe-count assumption

E010 recovered the tested zero-payload workloads with
`maxExportBatchSize=100`, but that value was only a count proxy for a byte
limit. E011 registered a new payload dimension before execution to ask whether
the same 100-span chunk remains durable as one string attribute grows.

`RunDescriptor` gained `payloadAttributeBytes`, with zero as the legacy decode
default. The app validates 0...65,536, generates an ASCII `lab.payload` value of
that exact length on every span, records the value in the UI and immutable run
metadata, and exposes it through the background-transition runner. Reliability
Core tests and the regenerated Simulator build passed before evidence capture.

The accepted matrix held total spans and batch count at 100:

| Persistence | Payload / span | Flush | File | Received |
|---|---:|---:|---:|---:|
| Instant | 0 | 55.78 ms | 107,789 bytes | 100/100 |
| Instant | 1,024 | 48.17 ms | 213,715 bytes | 100/100 |
| Instant | 1,536 | 48.88 ms | 0 | 0/100 |
| Instant | 2,048 | 49.36 ms | 0 | 0/100 |
| Default | 1,024 | 51.93 ms | 213,688 bytes | 100/100 |
| Default | 1,536 | 49.04 ms | 0 | 0/100 |

Every background event preceded the 15-second schedule. Loss conditions made
no HTTP attempt before or after relaunch and left no persistence file. Flush
still completed, with durations overlapping successful conditions.

Adding 1,024 bytes to each of 100 spans increased the instant file by 105,926
bytes. Extending the observed shape by another 512 bytes per span projects an
object near 264,915 bytes, just above the 262,144-byte ceiling. The actual
1,536-byte runs then supplied the stronger observation: zero durable bytes and
zero receipts for both presets.

The conclusion is deliberately narrower than “large attributes are bad.” At a
fixed count of 100, one plausible schema change moved durability from complete
to absent without changing the apparent flush result. Count configuration alone
cannot enforce a byte contract.

## E012 recovered the same payload by changing object partitioning

E012 preregistered a matched intervention before execution. It kept total spans,
payload, preset, real background callback, unavailable collector, direct
`SIGKILL`, and relaunch procedure fixed, and changed only
`maxExportBatchSize` from 100 to 50.

All four registered conditions recovered exactly:

| Persistence | Payload / span | Flush | File | Request | Received |
|---|---:|---:|---:|---:|---:|
| Default | 1,536 | 119.46 ms | 264,897 bytes | 183,618 bytes | 100/100 |
| Default | 2,048 | 123.86 ms | 316,057 bytes | 234,818 bytes | 100/100 |
| Instant | 1,536 | 82.22 ms | 264,891 bytes | 183,618 bytes | 100/100 |
| Instant | 2,048 | 215.90 ms | 316,107 bytes | 234,818 bytes | 100/100 |

No first process made an HTTP request. Each relaunch made one successful request
and produced no missing, duplicate, unexpected, or generation-gap sequence.

One initially surprising observation strengthened the source interpretation:
the persistence files were roughly 265 or 316 KB, larger than the 256-KiB
object ceiling. That is expected because two individually valid 50-span objects
were appended to one file. The separate file limit is 4 MiB. On resume, the two
objects were flattened into one OTLP body, so partitioning storage did not add a
second observed transport request.

This E011/E012 pair is the cleanest intervention so far: the same logical data
moved 100/100 → 0/100 when encoded bytes crossed a hidden boundary, then 0/100
→ 100/100 when only the persistence-object partition changed. It also shows why
batch 50 is not a final answer. A single span may be oversized even at batch 1,
and future attribute changes can invalidate another fixed count.
