## Pinned source revealed two retry owners

Source inspection at `opentelemetry-swift` 2.5.0 found two copies retained after
one failure:

- The persistence worker keeps the encoded file when its decorated export says
  retry is needed.
- `OtlpHttpTraceExporter` restores the complete failed outgoing array to its own
  in-memory `pendingSpans`.

On the next file retry, the HTTP exporter appends the same 100 spans to its
pending copy. A failed 100-span request can therefore become a 200-span request,
then a 300-span request after another failure.

## E005 moved recovery across a process boundary

The next question was whether E004's exact recovery depended on keeping the
original process alive. A resume launch path was added before running the
experiment. It configures telemetry for an existing run ID and persistence
directory but does not create a new `RunDescriptor`, rewrite evidence, or

E005 deliberately used the stateless exporter so process durability could be

Neither first process made an HTTP attempt before termination. Each resumed

The observed-file stop rule is a strength for this lifecycle claim and a limit

## E006 found the gap before persistence begins

E005 intentionally waited for a persistence file before terminating, so it
could only test discovery by a new process. E006 moved the trigger earlier. The
host waited for the independent 100-record generated ledger, then requested an
abrupt stop at registered offsets of 0, 50, 150, or 300 milliseconds. The
Collector was started only after the first process stopped.

Pinned-source inspection showed why this boundary matters. The configured
`BatchSpanProcessor` can retain ended spans for its 0.25-second schedule delay
before calling the persistence exporter. Instant performs a synchronous append
once called; default schedules the append asynchronously. Neither preset makes
the earlier `span.end()` call itself durable.

### The first stop mechanism invalidated the timing assumption

The first registered default zero-offset run used `simctl terminate`. No file
was visible before the request, but the command needed about 471 milliseconds
to return. One complete file appeared during that interval, and resume recovered
100/100. Treating that as a real zero-offset result would have produced the
wrong conclusion.

The evidence was preserved as a calibration run. The protocol was amended
before continuing: subsequent runs sent `SIGKILL` directly to the Simulator app
PID. A tiny compiled UTC timestamp probe replaced Perl process startup, and two
nonessential critical-path probes were removed. One replacement run was added
without deleting or reusing the original run ID.

### Abrupt-stop matrix

| Persistence | Registered wait | Ledger observed → signal | File before | Received | Missing |
|---|---:|---:|---|---:|---:|
| Default | 0 ms | 55 ms | no | 0 | 100 |
| Default | 0 ms | 14 ms | no | 0 | 100 |
| Default | 50 ms | 73 ms | no | 0 | 100 |
| Default | 150 ms | 181 ms | no | 0 | 100 |
| Default | 300 ms | 331 ms | yes | 100 | 0 |
| Instant | 0 ms | 19 ms | no | 0 | 100 |
| Instant | 300 ms | 328 ms | yes | 100 | 0 |

Every loss run had no file after termination, no HTTP attempt after resume, and
0/100 receipts. Every 300-ms run had a complete file before the signal, made one
27,818-byte request after resume, and recovered 100/100 at exactly 1x. No partial
batch was observed. Ledger and metadata hashes matched across resume in every
condition.

The current evidence brackets an end-to-end transition in this Simulator setup:
an effective 181 ms still lost all 100, while effective 328/331 ms conditions
were already durable. This must not be reported as a universal millisecond SLA;
polling, host instrumentation, process scheduling, and the position of the
independent ledger all affect the values.

The stronger conclusion is semantic: persistence can recover a file that
exists, but it cannot recover spans killed in an upstream batch window. The
durability boundary measured here is the file, not `span.end()` and not the
configuration flag that enabled persistence.

## E007 closed the observed gap with a cooperative flush

E006 showed total loss when the process stopped before `BatchSpanProcessor`
handed the batch to persistence. E007 tested an intervention rather than merely
adding more timing points.

A new `durabilityBarrier` flush mode was added without changing the meaning of
the historical `explicit` mode. Run lifecycle evidence now records generated
ledger commit, flush start, flush completion, burst completion, and monotonic
flush duration. The new barrier first calls provider force-flush, then directly
flushes the configured top-level exporter. For the persistence decorator that
waits for queued writes and invokes its export worker.

ReliabilityCore gained a lifecycle-event model and barrier parsing coverage.
After these changes, 16 tests in 8 suites passed, and the Simulator integration
build passed.

The host waited for the app's flush-completed event, checked file state, and
sent direct `SIGKILL` with zero additional registered delay:

| Persistence | Flush | Duration | File before stop | First-process HTTP | Received |
|---|---|---:|---|---|---:|
| Default | provider only | 37.27 ms | yes | none | 100/100 |
| Instant | provider only | 74.04 ms | yes | none | 100/100 |
| Default | durability barrier | 100.11 ms | yes | 1 failure | 100/100 |
| Instant | durability barrier | 88.32 ms | yes | 1 failure | 100/100 |

All four files survived the abrupt stop and were deleted after one exact
recovery. In barrier runs, attempt 1 happened before flush completion and failed
with connection refused; after relaunch attempt 2 sent the same 27,818-byte body
and succeeded. The stateless exporter kept the retry body constant.

The minimum successful intervention in this matrix was provider force-flush.
Compared with E006's 0/100 zero-offset controls, waiting for its completion
changed recovery to 100/100 for both presets. The extra exporter barrier did not
improve recovery. It added an immediate failed network request and measured
blocking: +62.84 ms for default and +14.28 ms for instant versus their one
provider-only run.

Pinned source still leaves a caveat for default: provider force-flush waits for
the batch export operation, while default persistence schedules its append on a
private async queue. That append happened to finish before the host check. E007
demonstrates empirical sufficiency under this timing, not a formal guarantee
that provider flush always implies durable default storage.

The larger lifecycle caveat is also intentional. The synthetic app called
flush after its burst, and the host cooperatively waited for completion. A real
scene background transition, suspension deadline, and jetsam do not promise
that window. Testing the same intervention from actual iOS lifecycle callbacks
is the next boundary.

## E009 broke the successful intervention with a larger batch

E009 registered 100, 500, and 1,000-span background flushes for both presets.
The first default 100-span run immediately exposed a protocol problem: although
Safari was requested after ledger observation, the Simulator delivered the
background event 6.30 seconds later, beyond the five-second schedule. Its
2.77-ms flush and 100/100 recovery were preserved but excluded.

Before any larger condition ran, the plan was amended to a 15-second schedule.
The runner gained an app-timestamp ledger-to-background check and now marks a
run invalid when lifecycle delivery crosses its configured schedule boundary.

The accepted matrix contradicted the complete-recovery hypothesis:

| Persistence | Planned | Flush duration | File bytes | Received | Surviving sequences |
|---|---:|---:|---:|---:|---|
| Default | 100 | 111.96 ms | 107,791 | 100/100 | 1...100 |
| Default | 500 | 167.32 ms | 0 | 0/500 | none |
| Default | 1,000 | 289.89 ms | 250,297 | 232/1,000 | 769...1,000 |
| Instant | 100 | 208.35 ms | 107,785 | 100/100 | 1...100 |
| Instant | 500 | 196.76 ms | 0 | 0/500 | none |
| Instant | 1,000 | 220.38 ms | 250,307 | 232/1,000 | 769...1,000 |

Every background event was before 15 seconds and every provider flush reported
completion. No first process made an HTTP attempt. Default and Instant still
produced exactly the same delivery boundary, so the first idea—an async default
writer race—could not explain the full matrix.

Pinned source exposed a count-versus-byte composition bug. The lab configured
`maxExportBatchSize=256`, so force-flush partitions 1,000 spans as
256 + 256 + 256 + 232. Persistence JSON-encodes each entire chunk as one object,
but both presets cap one object at 256 KiB. The file writer swallows the
oversize error and returns no status; the outer persistence exporter still
reports success to the processor.

The evidence matched that source path exactly. For 1,000 spans, the first 768
sequences disappeared and the final 232 produced a roughly 250-KB file. For 500
spans, neither the 256- nor 244-span encoded object fit, leaving no file. Instant
synchronous writing cannot append an object rejected by the shared size policy.

This is stronger than a simple performance curve. `forceFlush` completed in all
runs, but completion concealed total or partial data loss. Span-count batching
and byte-sized storage limits are different units, and payload attributes can
move their collision point. The next intervention should lower export chunk
size before changing any persistence code, then rerun the same 500/1,000
workloads to see whether 0/232 can become exact recovery.

## E010 changed only the count side of the boundary

E010 registered a configuration intervention before implementation: record
`maxExportBatchSize` in immutable run metadata, decode historical evidence as
256, and rerun 500/1,000 spans with the value lowered to 100. Persistence code,
payload, lifecycle callback, 15-second schedule, stateless exporter, and abrupt

ReliabilityCore and automation gained the new dimension with legacy decoding
coverage. All 17 tests in 8 suites passed. The app then used the recorded value
to construct `BatchSpanProcessor`, exposed it in the UI, and passed a regenerated
Simulator build.

The intervention restored every direct comparison:

|---|---:|---:|---:|---:|
| Default | 500 | 0/500 | 500/500 | 147.76 ms |
| Default | 1,000 | 232/1,000 | 1,000/1,000 | 169.19 ms |

All four runs had one persistence file before direct `SIGKILL`, no first-process

This matched intervention changes the E009 mechanism from inference to an

moved each encoded object below the byte ceiling and restored the exact missing
identities: +500 at the 500 workload and +768 at the 1,000 workload for both
presets.

The number 100 remains payload-specific. E010 does not make the SDK byte-aware,
surface swallowed writer errors, or protect one span with an unusually large
attribute. It demonstrates the smallest tested configuration remedy for this
payload and supplies a direct “0 to all” article comparison.
