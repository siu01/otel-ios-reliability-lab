## Pinned source revealed two retry owners

Source inspection at `opentelemetry-swift` 2.5.0 found two copies retained after
one failure:

- The persistence worker keeps the encoded file when its decorated export says
  retry is needed.
- `OtlpHttpTraceExporter` restores the complete failed outgoing array to its own
  in-memory `pendingSpans`.

On the next file retry, the HTTP exporter appends the same 100 spans to its
pending copy. A failed 100-span request can therefore become a 200-span request,
then a 300-span request after another failure.

## E003 observed request amplification directly

An HTTP client wrapper recorded request start/completion events without changing
the official `BaseHTTPClient` request or result. The pre-registered timing matrix
produced:

| Collector delay | Completed HTTP failures | Successful body bytes | Total received | Multiplicity |
|---:|---:|---:|---:|---:|
| 4 s | 0 | 27,818 | 100 | 1x |
| 6 s | 1 | 55,418 | 200 | 2x |
| 8 s | 2 | 83,018 | 300 | 3x |
| 10 s | 2 | 83,018 | 300 | 3x |

Every failure was a connection-refused completion within milliseconds, not a
two-second semaphore timeout. The successful request body grew by 27,600 bytes
per completed failure. Collector reconciliation matched it exactly, and each
replayed logical span retained the same trace ID and span ID.

The ten-second run remained 3x because backoff permitted only two completed
failures before recovery. Failure count, rather than outage seconds alone, was
the direct multiplicity predictor in this matrix.

## E004 intervened on retry ownership

E003 explained amplification, but a source explanation plus correlation was not
enough. A lab `StatelessOtlpHTTPTraceExporter` was added. It creates the OTLP
protobuf request from the supplied `SpanData` and reports the HTTP result without
retaining failed spans. The official persistence decorator remains the only
layer that owns retry state.

The exporter mode was added to run metadata with backward decoding to
`officialStateful`. Automation and UI can select either mode. The new Swift file
was included by regenerating the Xcode project before the first build; the
Simulator build passed.

E004 results:

| Delay | Completed failures | Body bytes by attempt | Total received | Duplicate | Missing |
|---:|---:|---|---:|---:|---:|
| 8 s | 1 | 27,818 → 27,818 | 100 | 0 | 0 |
| 10 s | 2 | 27,818 → 27,818 → 27,818 | 100 | 0 | 0 |

The direct ten-second comparison is the strongest intervention: E003's official
stateful exporter also completed two failures but grew to an 83,018-byte success
and 300 receipts. E004 kept the 27,818-byte body and delivered 100 exactly once.

Single-owner retry therefore preserved full recovery and stopped amplification
under both registered durations. The lab exporter remains a mechanism proof, not
a production-parity replacement for all official exporter features.
